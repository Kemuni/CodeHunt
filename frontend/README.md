# Frontend CodeHunt / Track Dev

Краткий контекст для разработчиков и ИИ. Приложение содержит лендинг, публичный каталог учебных задач и административный редактор с черновиками. Перед изменениями прочитайте [AGENTS.md](AGENTS.md): документация установленного Next.js находится в `node_modules/next/dist/docs/`.

## Стек и запуск

Next.js 16 App Router, React 19, TypeScript, Tailwind CSS 4. UI основан на Base UI, формы — React Hook Form + Zod, запросы и кэш — TanStack Query, уведомления — Sonner. Для сортировки используется dnd-kit, для карусели — Embla. Версии и команды: [package.json](package.json). Алиас `@/` указывает на корень frontend.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

Страница открывается на `http://localhost:3000`. В `.env.local`: `BACKEND_API_URL` — адрес backend (по умолчанию `http://127.0.0.1:8000`), `GITHUB_ID` и `GITHUB_SECRET` — GitHub OAuth App, `NEXTAUTH_SECRET` — случайный секрет cookie, `NEXTAUTH_URL` — полный адрес frontend. Backend, PostgreSQL и MinIO запускаются отдельно; схема БД должна быть подготовлена. Frontend не выполняет миграции.

## Маршруты и точки входа

| Маршрут                  | Назначение / компонент                                            |
| ------------------------ | ----------------------------------------------------------------- |
| `/`, `/for-company`      | Лендинги; `components/landing/`, формы связи в `contact-me.tsx`   |
| `/tasks`                 | Публичный каталог — `components/tasks/task-catalog.tsx`           |
| `/tasks/[slug]`            | Просмотр — `components/tasks/task-details.tsx`                    |
| `/admin/tasks`           | Управление задачами и черновиками — тот же каталог с `admin`      |
| `/admin/tasks/editor`    | Новая задача; `?draftId=` открывает черновик, `?taskId=` — задачу |
| `/api/backend/[...path]` | Серверный прокси запросов к `/api/...` backend                    |

Файлы `app/**/page.tsx` задают маршруты и проверяют параметры. UI находится в `components/`. Общие шапка, подвал и шрифты — в `app/layout.tsx`, QueryClient и toast — в `components/providers/providers.tsx`, тема — в `app/globals.css`.

## Каталог

`TaskCatalog` и `task-catalog-controls.tsx` используются в `/tasks` и `/admin/tasks` (вкладка задач). Поиск через InputGroup с лупой, фильтры через DropdownMenu: диапазон сложности 0–10, направления frontend/fullstack, бесплатные/по подписке. Счётчик над иконкой показывает количество активных групп фильтров. Очистка сбрасывает только фильтры, сохраняя поиск и сортировку. Сортировка — новые (по умолчанию в UI), старые, название, простые, сложные.

Изменения поиска и фильтров объединяются за 300 мс, запросы отменяются при смене параметров, пагинация сбрасывается вместе с новым запросом. Предыдущие карточки остаются на экране до ответа. Backend фильтрует весь каталог до пагинации. Черновики используют отдельный список.

Чекбокс «Доступ по подписке» в редакторе записывает `is_paid`: у черновика автосохранение, у опубликованной задачи — кнопка сохранения. Карточки и детали показывают соответствующий бейдж. Требуется backend-миграция `0a9d72e4b831`; существующие задачи бесплатные. Оплата и проверка подписки пользователя — отдельный будущий функционал.

## Данные и редактор

- [task-contract.ts](lib/api/task-contract.ts) — типы ответов и запросов API. [request.ts](lib/api/request.ts) разбирает `{ success, data, errors }` и создаёт `ApiError` со статусом, кодом и ошибками полей. Операции задач — `lib/api/tasks.ts`, файлов — `lib/api/task-media.ts`.
- Запросы задач идут через Next.js-прокси. Он передаёт серверную Bearer-сессию вошедшего пользователя из зашифрованной HttpOnly cookie. Вход/выход выполняет NextAuth через GitHub; /admin защищён серверным layout и проверками backend. Роль задаётся подтверждёнными email в ADMIN_EMAILS backend. Контактные формы используют тот же `apiRequest` и прокси через `lib/api/contact.ts`; отдельного публичного адреса backend им не требуется.
- Единственный тип уровня — [TaskLevel](lib/tasks/task-level.ts): `Easy = "easy"`, `Medium = "medium"`, `High = "high"`. Русские подписи находятся в `lib/tasks/labels.ts`; `base` и `maximum` больше не используются как значения уровней.
- Ответ задачи: `presets.easy`, `presets.medium`, `presets.high`. Каждый содержит `{ preset, complications }`; `preset` может быть `null`. `complications` содержит только собственные пункты уровня, включая вложенные и пустые группы. Не добавляйте наследование пунктов между уровнями.
- Запись в API использует другой формат: массив `presets` и дерево `items`. Преобразования чтения/записи сосредоточены в [editor-model.ts](lib/tasks/editor-model.ts).
- Внутренняя модель редактора: `TaskNode`, категория с `children` или пункт с `title`, `description`, `criteria`, `required`, `difficultyLevel`. Операции дерева — `task-tree.ts`, reducer — `task-items-state.ts`. Используйте `nodeKey`: числовой ID категории может совпадать с ID пункта. Глубина категорий ограничена тремя уровнями.
- [use-task-editor.ts](hooks/tasks/use-task-editor.ts) управляет загрузкой, сохранением и файлами; компонент `editor/task-editor.tsx` собирает UI. Локальное редактирование дерева обслуживает `use-task-items.ts`.
- [draft-coordinator.ts](lib/tasks/draft-coordinator.ts) последовательно выполняет автосохранение, операции файлов и публикацию с актуальной `revision`. Пустая нетронутая форма не создаёт черновик. Конфликт ревизии сохраняет локальные правки и требует явного разрешения; не обходите очередь параллельными запросами.
- Для существующей задачи основная информация и пункты сохраняются явно; фотографии и вложения изменяются сразу. Удаление задачи/черновика подтверждается; опубликованная задача сначала архивируется, черновик удаляется с проверкой ревизии.

## Общие UI-компоненты

`components/ui/` содержит примитивы и layouts, `components/reui/` — дополнительные компоненты, включая sortable. Компоненты, нужные только одному экрану, остаются рядом с ним или внутри его файла.

- `tasks/task-requirement-card.tsx` и `tasks/task-requirement-group.tsx` — общий UI пунктов и групп для просмотра и редактора. Редактор передаёт меню, сортировку и форму через props/slots. Содержимое свёрнутых групп остаётся смонтированным, чтобы не терять ввод.
- `tasks/task-difficulty.tsx` — диапазон сложности с иконкой. `tasks/expandable-text.tsx` — сокращение длинного текста.
- `ui/responsive-modal.tsx` — Dialog на широком экране, Drawer на телефоне. `ui/confirm-dialog.tsx` — подтверждение на базе AlertDialog; вызывающий компонент управляет выполнением действия и закрытием.
- `ui/layouts/page.tsx` — оболочка страницы; `ui/layouts/section.tsx` — карточки разделов. Для ссылки возврата справа от заголовка:

```tsx
<PageLayoutHeader text="Обзор задачи" backHref="/tasks" />
```

Без `backHref` кнопки нет. Это переход по указанной ссылке, а не возврат по истории браузера. На странице задачи фото и основная информация расположены сверху, описание и три уровня — внутри ТЗ. По умолчанию видны четыре пункта каждого уровня; группы не считаются пунктами. Вложения открываются из ТЗ в адаптивном окне, для скачивания используется постоянный URL из ответа API.

## Проверки и порядок работы

```bash
npm run lint
npx tsc --noEmit --incremental false
npm test
npm run build
```

Unit-тесты лежат рядом с моделью редактора и компонентами. Для E2E нужен запущенный frontend и браузер Playwright. С установленным Chrome:

```bash
E2E_BASE_URL=http://localhost:3000 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e
```

Без `E2E_LIVE_API=1` проверки с настоящим backend пропускаются. Добавьте эту переменную для полного прогона: нужны доступные backend, БД, MinIO и администратор. Live-тесты создают собственные записи и удаляют их в `finally`; остальные подменяют API-ответы. Для изолированного прогона используйте `E2E_ISOLATED_AUTH=1 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`: Playwright сам запускает Next.js на localhost:3100 и тестовый backend на 8101 с тестовыми секретами. Для live-тестов необходим `E2E_STORAGE_STATE` с сессией тестового администратора; файл с cookie не коммитить. Конфигурация — `playwright.config.ts`, сценарии — `e2e/`.

Для новой задачи: найдите маршрут и компонент → проверьте контракт и преобразования → используйте существующий общий UI → измените нужный слой → выполните соответствующие проверки. При изменении API обновляйте контракт, преобразования и фикстуры вместе; при изменении редактора проверяйте сохранение, конфликт ревизий и сохранность формы внутри свёрнутых групп.


Настройка GitHub OAuth и миграция backend описаны в [development.md](../backend/docs/development.md#github-oauth). Callback для локального frontend: `http://localhost:3000/api/auth/callback/github`. Прокси не передаёт клиентские Authorization/X-User-ID; записи требуют Origin текущего сайта. Backend-токен не возвращается из `/api/auth/session`.

## Упрощённый API — 09.11.2026

Публичные ссылки используют slug, загрузка — `GET /tasks/by-slug/{slug}`. Внутренний редактор продолжает использовать ID. Административный список читает `/editor/tasks`, дубль `/all` удалён. Новая задача создаётся только через черновик.

Готовая задача сохраняется одним `PUT /editor/tasks/{id}`: поля, items и presets фиксируются атомарно, ответ TaskDetail сразу обновляет редактор. Последовательность частичных запросов и повторный GET убраны. Preset сохраняет ID своего уровня, пункты и группы сохраняют переданные ID. При ошибке локальный ввод остаётся в редакторе, частичного сохранения на backend нет.

Список черновиков использует DraftSummary с названием, описанием, revision, датами и cover_photo. Проверка ошибок выполняется при открытии и изменении формы, поэтому карточка списка больше не показывает потенциально устаревшую готовность к публикации.

Скачивание берёт resource.url из ответа, без запроса download-url. taskMediaUrl переводит адрес в общий `/api/backend/media/...`; cookie-сессию добавляет прокси, доступ проверяет backend. Редакторские медиадубли удалены. API решений и PATCH типа вложений сохраняются для будущего интерфейса. PATCH подписи вложения уже используется: кнопка карандаша открывает общий ResourceTitleEditor для черновика и задачи; revision черновика обновляется через DraftCoordinator. GET накопительной конфигурации заменены GET `/tasks/by-slug/{slug}/presets` и `/editor/tasks/{id}/presets`, возвращающими все уровни с собственными пунктами. UI получает тот же формат внутри TaskDetail без отдельного запроса.


### Live E2E в одноразовом окружении

Из frontend, с установленными зависимостями backend/frontend, запущенным Docker и Chrome:

```sh
PLAYWRIGHT_CHANNEL=chrome npm run test:e2e:live
```

Скрипт `backend/scripts/test_live_e2e.py` создаёт отдельные PostgreSQL 18, MinIO и Redis через Testcontainers, поднимает настоящий FastAPI и копию Next.js на свободных портах, запускает три сценария с тегом `@live`. Схема создаётся через create_all и удаляется через drop_all. Рабочие `.env`, БД и dev-серверы не используются. Тестовый администратор получает настоящую запись сессии backend и зашифрованную cookie NextAuth; обращений к реальному GitHub нет. Сервисы останавливаются, контейнеры и временная копия удаляются после прогона. Пути к серверным логам и Playwright-артефактам выводятся при запуске.

Сценарии: `e2e/task-editor.spec.ts` проверяет полный цикл черновик → файлы → публикация → редактирование → скачивание и восстановление после ошибки/конфликта revision. `e2e/task-deletion.spec.ts` проверяет удаление черновика и опубликованной задачи через каталог; подготовка задачи использует черновик → publish. Остальные E2E запускаются через `E2E_ISOLATED_AUTH=1 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e -- --grep-invert @live`.

Проверки 09.11.2026: полный backend pytest — **88 passed**, покрытие **96,87%**. Frontend — **56 unit-тестов**, **37 изолированных E2E + 3 live E2E = 40 passed, без пропусков**. Live-тесты прошли с настоящими FastAPI/PostgreSQL/MinIO/Redis, включая файлы, публикацию, атомарное редактирование, удаление и конфликт revision. TypeScript, ESLint изменённых файлов, Ruff/format и ty прошли. Рабочая БД и реальные GitHub-аккаунты не использовались.

09.11.2026 удалён публичный GET `/tasks/{id}`. Live E2E читают детали по `/tasks/by-slug/{slug}`, как и frontend. Скрипт live-прогона не является частью приложения: без него окружение и сессию тестового администратора нужно подготовить отдельно.


Фотография обязательна перед сохранением/публикацией задачи; черновик можно оставить без неё. В готовой задаче кнопки удаления последнего фото и полной очистки отключены, backend также проверяет это правило. Для замены сначала загрузите новое фото, затем удалите старое. JPG/JPEG принимаются по расширению даже при пустом MIME браузера, содержимое проверяет backend.

Осталась одна функция `taskMediaUrl(url)` для фотографий и вложений. В `task-contract.ts` удалены неиспользуемые тела DraftCreate/Update/Publish, CompositionUpdate, GalleryUpdate/DraftGalleryUpdate и ErrorResponse/ErrorDetail. Общие поля TaskRead/TaskDetail/TaskSave, тип ResourceRead с url и Page<T> устраняют дублирование. Остальные типы описывают используемые запросы, ответы и вложенные структуры.
