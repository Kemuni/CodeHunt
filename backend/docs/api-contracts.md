# Контракты API

Актуально на 09.11.2026 после упрощения API. Источник истины — `/openapi.json`; пути ниже имеют префикс `/api`. Frontend вызывает их через `/api/backend/...`, а GitHub-аутентификация обращается к backend с сервера Next.js.

## Ответы и доступ

Успех: `{success: true, data: ..., errors: null}`. Ошибка: `{success: false, data: null, errors: {code, message, details}}`. Health-check сохраняет `{status: "ok"}`. Пагинация: `{items, total, limit, offset}`, limit от 1 до 100, по умолчанию 20.

Backend принимает Bearer-сессию, созданную `POST /auth/github`. `GET /auth/me` возвращает текущего пользователя, `POST /auth/logout` отзывает сессию. Администраторы определяются подтверждёнными email из ADMIN_EMAILS. Next.js хранит токен в защищённой cookie, не отдаёт его клиентскому JavaScript, проверяет Origin мутаций и не доверяет клиентским Authorization/X-User-ID.

## Библиотека

`GET /task-complications/library` возвращает массив направлений `{developer_type, categories}` с деревом категорий, их children и complications. Поддерживаются q и developer_type. Создание/изменение/удаление категорий и шаблонов доступны администратору. Отдельные GET списка и одного элемента удалены: интерфейс использует дерево библиотеки.

Категория: title, parent_id, developer_type. Шаблон: category_id, title, description; slug отсутствует. Используемый шаблон защищён от изменения текста и удаления. Правки ссылок проверяются backend, существующие ограничения дерева сохраняются.

## Каталог и детали

`GET /tasks`: только published и is_hidden=false. Карточка TaskRead включает cover_photo, но не всю галерею. Общие параметры публичного и редакторского каталогов:

- `q`: поиск без учёта регистра по названию и краткому описанию; пробелы по краям удаляются, `%` и `_` считаются обычными символами. Максимум 300 символов.
- `developer_type`: frontend/fullstack; можно повторять параметр для выбора нескольких направлений (ИЛИ).
- `difficulty_min`/`difficulty_max`: пересечение с диапазоном задачи, границы от 0 до 10 включительно.
- `access`: free/subscription, фильтрация по `is_paid`; отсутствие параметра включает оба вида.
- `sort`: oldest (API по умолчанию), newest, title, difficulty_asc, difficulty_desc. По сложности сравниваются сначала нижняя граница для asc или верхняя для desc, затем другая граница. ID разрешает равенства для стабильной пагинации.
- `level`, `parent_task_id`, `limit`/`offset` сохраняются. Все фильтры и сортировка выполняются до пагинации; total учитывает фильтры.

Публичные страницы frontend имеют адрес `/tasks/{slug}` и читают `GET /tasks/by-slug/{slug}`. `GET /tasks/{task_id}` удалён; публичные детали читаются только по slug и скрывают архивные и скрытые задачи. В редакторе и маршруте создания решения используются ID.

`GET /editor/tasks` доступен администратору, принимает те же фильтры и сортировку, дополнительно status и is_hidden. Дубль `/editor/tasks/all` удалён.

`is_paid` — boolean, по умолчанию false. Возвращается в TaskRead/TaskDetail, записывается через payload черновика, публикацию, PUT и PATCH задачи (null запрещён). Определяет подпись «Бесплатно»/«По подписке» и фильтрацию каталога. Это признак задачи: биллинг и проверка наличия подписки пользователя пока не реализованы; правила доступа к деталям и медиа остаются основанными на публикации, скрытости и роли.

TaskDetail содержит поля задачи, cover_photo, photos, resources и объект presets с ключами easy/medium/high. Каждый блок — `{preset, complications}`: метаданные пресета либо null и собственное дерево уровня, включая пустые группы. Пункты имеют вычисляемый order_number с 1 внутри своего уровня; группы номера не имеют. В БД хранится position. Файлы содержат постоянные URL, object_key наружу не выдаётся.

## Создание и атомарное редактирование

Новые задачи создаются только через TaskDraft и `/publish`; `POST /editor/tasks` удалён.

`PUT /editor/tasks/{id}` принимает TaskSave: все поля TaskCreate, обязательный массив items и обязательный массив presets (не более трёх уникальных уровней). Поле status не входит в полную запись: архивирование и публикация существующей задачи выполняются PATCH. Отсутствующие необязательные поля полного PUT принимают значения по умолчанию.

Информация, пресеты и дерево сохраняются одной транзакцией. Возвращается весь TaskDetail, повторный GET не нужен. Preset идентифицируется уровнем: оставшийся уровень сохраняет ID; отсутствующий удаляется, новый создаётся. В items существующие группы/пункты передают id, новые — без id. Вложенность и порядок массива задают parent и position. Лимиты — 10 уровней, 1000 элементов; потомки группы имеют её level. Повторные/чужие ID отклоняются. При изменении текста связанного пункта требуется явно подтвердить complication_id или передать null.

Пропущенные элементы удаляются. Ссылки решений блокируют удаление используемых пунктов и пресетов. Проверка опубликованной задачи выполняется по итоговому составу, а любая ошибка откатывает всё, включая поля и даты. ID оставшихся элементов и снимки решений сохраняются. Атомарность не заменяет контроль версий: у Task нет revision.

Удалены точечные операции `/complications`, самостоятельные операции записи пресетов и `/composition`: их заменяет полный PUT. `PATCH /editor/tasks/{id}` остаётся для частичных изменений, включая status/is_hidden. DELETE разрешён только неиспользуемой архивной задаче.

## Черновики

TaskDraft принадлежит конкретному администратору. POST сохраняет `{payload}`; GET одного, PATCH и операции файлов возвращают полный DraftRead с payload, revision, validation_errors, is_valid, photos, resources. PATCH принимает `{revision, payload}`, объединяет поля формы, массивы заменяет целиком. Revision обязательна также для файловых мутаций, удаления и публикации. Конфликт возвращает 409; права другого администратора не дают доступа к чужому черновику.

`GET /editor/task-drafts` возвращает Page[DraftSummary]: id, title, short_description, revision, created_at, updated_at, cover_photo. Полное дерево, вложения и ошибки в список не включаются. Не выполняется валидация каждой формы; обложки читаются одним пакетным запросом. Пустое/нестроковое название возвращается как пустая строка. Проверка актуальности slug и ссылок остаётся при открытии, сохранении и публикации.

`POST /editor/task-drafts/{id}/publish` принимает `{revision}` и возвращает TaskDetail с HTTP 201. Создаёт задачу и переносит файлы одной транзакцией, сохраняя ID и ключи объектов MinIO. Повторная публикация уже удалённого черновика даёт 404.

## Пресеты без накопления

GET `/tasks/by-slug/{slug}/presets` возвращает пресеты публичной опубликованной задачи; GET `/editor/tasks/{task_id}/presets` доступен администратору для задачи любого состояния. Формат совпадает с `TaskDetail.presets`: `{easy, medium, high}`, в каждом блоке `{preset, complications}`. Поле `preset` равно null, если пресет уровня отсутствует. Пункты и вложенные группы относятся только к своему уровню, пустые группы сохраняются. Номера пунктов начинаются с 1 внутри каждого уровня. Нижние уровни в medium/high не включаются. Публичный маршрут возвращает 404 для скрытой/архивной задачи даже администратору, редакторский требует административную сессию.

Frontend продолжает брать эти же данные из TaskDetail без дополнительного запроса. Новый отдельный API позволяет получить только состав уровней без загрузки описания, фото и вложений.

## Файлы и медиапрокси

Фото: POST `.../photos` с multipart files, PUT `.../photos` с `{photo_ids}`. Для черновика добавляется revision. От одного до четырёх фото для готовой задачи; первое титульное. Черновик может не иметь фото, тогда is_valid=false с ошибкой photos/missing_photo, а публикация вернёт 422. Пустой массив очищает только галерею черновика; у задачи удаление последнего фото запрещено (missing_photo). Сохранение готовой задачи и перевод в published также проверяют фото. Чтение старых задач без фото сохранено, при сохранении их нужно дополнить.

Статичные JPEG/PNG/WebP, до 10 МиБ и 20 млн пикселей. Формат определяется содержимым, а не расширением или MIME от браузера. Обычный и прогрессивный JPG сохраняются без перекодирования; MPO (JPEG с дополнительными кадрами) преобразуется в основной JPEG-кадр с учётом EXIF-ориентации. Размер результата также проверяется. Ограничения разрешения, неподдерживаемый формат и ошибка декодирования сообщаются раздельно.

Вложения: POST `.../resources` с multipart file, title и type (design/specification/asset/other). Для черновика title/type имеют значения по умолчанию, revision обязательна. PATCH меняет название/тип, DELETE удаляет вложение. Максимальный размер 50 МиБ. У задачи POST/PATCH возвращают ResourceDownloadRead с url, у черновика файловые мутации возвращают DraftRead.

Фото доступны через GET/HEAD `/media/photos/{id}`, вложения — GET/HEAD `/media/resources/{id}`. Отдельные `/editor/media/...` и все `/download-url` удалены. Клиент берёт URL из TaskDetail, DraftRead или ответа загрузки. Доступ проверяется по метаданным и сессии перед Redis, выдачей байтов, HEAD или 304. Публичное опубликованное задание доступно гостю; скрытое/архивное — администратору; черновик — его владельцу-администратору. Поэтому объединение адресов не открывает закрытые файлы.

Ответы используют ETag, `Cache-Control: private, no-cache` и для вложений Content-Disposition с исходным именем. Redis кеширует байты с TTL, при сбое читается MinIO. Подписанные S3-ссылки и настройки S3_PUBLIC_ENDPOINT_URL/S3_URL_TTL удалены.

Удаление файла/владельца сохраняет очистку в pending_file_deletions в транзакции метаданных. После commit выполняется попытка удаления MinIO; при сбое очередь повторяется, attempt_count увеличивается. Общие ключи проверяются пакетно по обеим таблицам. Удалённые записи сразу недоступны через медиапрокси. Старые объекты без метаданных автоматически не ищутся.

## Сохранённый будущий функционал

Весь API решений сохранён: создание из пресета, снимки, собственные пункты, порядок, независимое завершение пунктов/решения, чтение, изменение и удаление. Решения доступны только автору. Medium включает easy+medium, high — все уровни. Любые пункты можно исключать. Изменение источника не переписывает снимки.

Сохранены оба PATCH вложений (Task/TaskDraft) для будущего редактирования названия и типа. Внешние GET `.../presets/{preset_id}/configuration` удалены: frontend их не использовал. Внутренний накопительный расчёт `composition.configuration` продолжает использоваться при создании решения.

## Контактные формы

POST `/contact-request/candidate` и `/contact-request/employer` сохранены. Обе формы frontend используют общий apiRequest через Next.js-прокси и общий формат ошибок; отдельный NEXT_PUBLIC_API_URL им не нужен.
