# Запуск, миграции и проверки

Сверено с Compose, Makefile, настройками и тестами 08.11.2026. Команды запуска относятся к локальному окружению. История миграций в репозитории не подтверждает их применение к конкретной БД.

## Локальный запуск

Из корня репозитория создать `.env` по `.env.example`, затем:

```sh
make sync-all
make up-dev-env
make migrate
make seed
make fastapi-dev
```

seed необязателен и запускается только явно. Он добавляет демонстрационных пользователей, категории, шаблон пагинации и два связанных задания с уровнями. Повторный запуск не дублирует записи, не исправляет существующие и не повышает права существующего пользователя.

| Команда из корня | Действие |
| --- | --- |
| make up-dev-env | PostgreSQL, MinIO, minio-init, Adminer и Redis |
| make stop-dev-env | Остановить инфраструктуру с сохранением контейнеров |
| make down-dev-env | Удалить контейнеры выбранных dev-сервисов, без удаления томов |
| make up-all | Собрать backend и запустить весь Compose |
| make down-all | Остановить и удалить контейнеры, тома сохраняются |
| make migrate | Alembic upgrade head рабочей локальной БД |
| make logs | Смотреть логи backend |
| make precommit-check | Ruff, форматирование, ty и pytest |

Docker entrypoint применяет `alembic upgrade head` перед запуском FastAPI с четырьмя workers. Создание схемы через metadata используется в тестах, не заменяет рабочие миграции.

## Настройки

`Settings` читает `../.env` относительно backend. Обязательны PROJECT_NAME и DATABASE_URL. Для обычного postgresql:// драйвер автоматически меняется на asyncpg, Alembic использует psycopg. Не выводить рабочие секреты в лог или документацию.

| Настройка | Назначение / default |
| --- | --- |
| S3_ENDPOINT_URL | Адрес для backend, в Compose http://minio:9000 |
| S3_PUBLIC_ENDPOINT_URL | Прежний адрес для подписанных URL; медиапрокси его не использует |
| S3_ACCESS_KEY, S3_SECRET_KEY | Учетные данные MinIO |
| S3_BUCKET | codehunt, для внешнего хранилища бакет создаётся заранее |
| S3_REGION | us-east-1 |
| S3_URL_TTL | 900 секунд, допустимо 1–604800 |
| MAX_PHOTO_BYTES | 10 МиБ |
| MAX_RESOURCE_BYTES | 50 МиБ |
| REDIS_URL | URL Redis для кэша фото, по умолчанию отключён, в Compose redis://redis:6379/0 |
| MEDIA_CACHE_TTL | Общий TTL фото и вложений: 300 секунд, допустимо 1–86400. PHOTO_CACHE_TTL принимается как прежнее имя, MEDIA_CACHE_TTL имеет приоритет |

minio-init создаёт приватный бакет повторяемой командой. Формирование постоянных URL фото и вложений не обращается к MinIO, включая download-url. Получение байтов при промахе Redis требует настроенного хранилища и может вернуть 503; отсутствие объекта обнаруживается при скачивании.

Порты по умолчанию: Redis 6379 (только loopback), PostgreSQL 5433, backend 8000, MinIO API 9000, MinIO Console 9001, Adminer 8080. Их переопределяют переменные Compose. PostgreSQL 18 сохраняется в том app-db-data под /var/lib/postgresql, MinIO — в app-minio-data.

Проверить **файлы** миграций без подключения: из backend `uv run alembic heads` и `uv run alembic history`. Проверка `alembic current` уже обращается к настроенной БД.

Особенности преобразования существующих данных:

- d53ae017b804 переводит старые Task.draft в скрытые архивные задания со всеми связями. У этих записей не было владельца, назначать его вымышленному администратору нельзя. Старые TaskDraft сохраняют payload. Откат блокируется, пока есть файлы, принадлежащие черновикам.
- e62b9c43a105 читает реальные данные. Смешанные группы разделяются по уровням, одна ветка сохраняет старый ID, другие получают новые. ID требований и ссылки решений сохраняются. Пустая группа получает минимальный уровень требований ближайшей непустой родительской ветки, иначе минимальный пресет задачи, иначе easy. Эти значения нужно проверить после миграции, прежнего явного намерения автора в БД не было.
- e62b9c43a105 преобразует items в TaskDraft и повышает revision изменённых форм. Старые открытые вкладки должны перечитать форму. Миграция блокирует таблицы групп, требований и черновиков, поэтому на время применения следует остановить запись. Для неё нужен online-режим, генерация всего перехода через `--sql` не заменяет миграцию данных.
- Откат e62b9c43a105 удаляет level групп, но не объединяет разделённые ветки обратно.
- a73f8d291b06 сохраняет ID шаблонов и связи, удаляя slug. Downgrade создаёт template-ID, исходные slug не восстанавливает.

Рабочую миграцию следует выполнять как отдельный шаг развёртывания с резервной копией. В документационном аудите она не применялась. Новые изменения контракта нельзя считать совместимыми со старым frontend автоматически.

## Тесты и статические проверки

Нужен работающий Docker. Testcontainers сам выбирает свободные порты PostgreSQL 18, MinIO и Redis и удаляет контейнеры после завершения. `docker compose up` для тестов не требуется. Ошибка Docker не означает, что тесты следует пропустить.

Из backend:

```sh
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest --cov=app --cov-report=term-missing
```

Эквиваленты из корня: make ruff-check, make ty, make test, make test-cov. Если .venv уже синхронизирована, можно использовать `.venv/bin/...`. Порог coverage — 80%, учитываются greenlet и thread.

`tests/conftest.py` до импорта приложения подставляет фиктивный DATABASE_URL и заменяет зависимость сессии на контейнер. Фикстура db создаёт все таблицы через Base.metadata.create_all и удаляет через drop_all. Тестовые пользователи: ID 1 админ, 2 обычный, 3 другой админ. В рабочем окружении эти ID не гарантируются.

Для недоступности S3 и проверки компенсации есть MemoryStorage. Проверки настоящих файлов используют MinIO Testcontainer. Общий сервис media.content использует get_storage напрямую, поэтому тесты байтов подменяют media.get_storage, а загрузки используют FastAPI dependency override.

**Известное исключение:** test_template_slug.py напрямую применяет upgrade/downgrade на вручную созданных таблицах отдельного контейнера. Это расходится с согласованным правилом create_all/drop_all и внесено в план. test_group_levels.py импортирует только чистый алгоритм преобразования для проверки данных без применения миграции.

Фактические результаты аудита и блокирующая регрессия — в [плане](task-domain-implementation-plan.md). Не переносить цифры прежнего прогона на новую версию.

## Нумерация и медиапрокси

Текущий head — `da6e4f719f31`; описание предыдущего перехода `c95f3d608e20` ниже. После обновления кода выполнить `make migrate` в рамках развёртывания. Эта ревизия удаляет order_number из task_complication_links и task_complication_link_groups, заменяет соответствующие части индексов на position и сохраняет позиции, ID и связи. API вычисляет номера при чтении. Downgrade восстанавливает сохранённые номера через обход дерева с 1 внутри каждого уровня. Предыдущая ревизия b84e2c507d19 сохраняется в истории для уже обновлённых БД; повторно изменять её для перехода на новую модель не нужно.

Перед запуском обновлённого backend выполнить `uv run alembic upgrade head` из backend в рамках развёртывания. b84e2c507d19 переносит старый order_number в position и обходит существующее дерево по уровням, сохраняя ID и связи. У каждого уровня свой счётчик с 1. Downgrade восстанавливает соседский порядок из position. Миграция данных требует online-подключения; рабочая БД при разработке и тестах не изменялась.

В b84e2c507d19 исправлена ошибка PostgreSQL `pending trigger events`: на время upgrade/downgrade связи `fk_link_group_parent` и `fk_task_link_group` проверяются немедленно, затем возвращаются в DEFERRED. Это позволяет чередовать UPDATE и ALTER TABLE без промежуточного commit. После неудачного запуска прежней версии можно повторить `make migrate` с исправленным файлом: PostgreSQL откатывает неудачную транзакцию. Не требуется вручную удалять ограничения или менять revision через stamp.

`make up-dev-env` теперь включает Redis. Для backend вне Docker включить кэш через `REDIS_URL=redis://127.0.0.1:6379/0 uv run fastapi dev`. В Compose URL настроен автоматически. Redis слушает опубликованный порт только на 127.0.0.1, имеет лимит 128 МиБ, политику allkeys-lru, не сохраняет кэш на диск. Сбой Redis не блокирует выдачу фото и вложений из MinIO. Общая реализация — services/media_cache.py; TTL задаётся MEDIA_CACHE_TTL. Для добавления кеша вложений новая миграция БД не нужна.

Фото доступны по `/api/media/photos/{id}`, вложения — по `/api/media/resources/{id}`; для редактора также есть `/api/editor/media/...`. Содержимое обоих типов хранится в Redis, а доступ проверяется по БД при каждом запросе, включая If-None-Match. Ответы private, no-cache требуют повторной проверки перед использованием браузерного кэша. Не переопределять это правило на CDN без проверки доступа на edge. На данном этапе CloudFront и signed cookies не разворачиваются. Их можно подключить отдельным этапом: [документация AWS](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-signed-cookies.html).

`private` разрешает хранить фото в браузере, запрещая общий HTTP-кэш посредников; `no-cache` требует повторной проверки, а не запрещает хранение (для запрета предназначен `no-store`). При совпадении ETag сервер возвращает 304 без байтов фотографии после проверки прав. Положительный max-age позволил бы браузеру показывать сохранённое фото без обращения к серверу в течение этого срока, включая ситуацию после скрытия задачи. См. [Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control).

Проверка личности использует Bearer-сессии GitHub. Frontend берёт сессию из зашифрованной HttpOnly cookie и передаёт через прокси. Next Image Optimization для закрытых изображений отключён, чтобы общий кэш оптимизатора не обходил проверку доступа.


## GitHub OAuth

1. В GitHub OAuth App укажите callback `http://localhost:3000/api/auth/callback/github` (в production — HTTPS-адрес frontend). Используйте один hostname и в браузере, и в NEXTAUTH_URL, и в callback.
2. Frontend `.env`/`.env.local`: `GITHUB_ID`, `GITHUB_SECRET`, `NEXTAUTH_URL=http://localhost:3000`, `NEXTAUTH_SECRET` (случайное значение, можно создать `openssl rand -base64 32`). Не используйте префикс NEXT_PUBLIC для секретов. `BACKEND_API_URL` — необязательный внутренний адрес backend; иначе используется NEXT_PUBLIC_API_URL.
3. Backend читает корневой `.env`, затем `backend/.env` (последний имеет приоритет; переменные процесса выше обоих). Задайте те же `GITHUB_ID` и `GITHUB_SECRET`, а также `ADMIN_EMAILS=admin@example.com,other@example.com`. Пробелы и регистр не влияют на сравнение. В Compose переменные backend поступают из корневого `.env`.
4. Выполните `make migrate` при развёртывании. Миграция `da6e4f719f31` добавляет users.github_id, users.verified_emails и auth_sessions. Существующие пользователи, задания и владельцы сохраняются; GitHub автоматически не привязывается к старой записи по совпадению email. Старый is_admin без подтверждённой GitHub-идентичности доступа не даёт.
5. Перезапустите frontend/backend. Войдите через GitHub; на первом входе создаётся аккаунт. Приватный подтверждённый email также учитывается. Чтобы обновить адреса после их изменения в GitHub, выйдите и войдите снова. Пустой ADMIN_EMAILS означает отсутствие администраторов; EDITOR_USER_ID удалён.

Протокол GitHub: [проверка OAuth-токена](https://docs.github.com/en/rest/apps/oauth-applications#check-a-token), [подтверждённые email](https://docs.github.com/en/rest/users/emails#list-email-addresses-for-the-authenticated-user). NextAuth v4 обслуживает OAuth state, PKCE, CSRF и cookie; дополнительная OAuth-библиотека не нужна.

Изолированные E2E: из frontend `E2E_ISOLATED_AUTH=1 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`. Playwright запускает тестовый backend на 8101 и Next.js на localhost:3100 с тестовыми секретами; PostgreSQL/MinIO/GitHub и рабочие данные не используются. Три live-теста пропускаются. Для live-прогона на отдельном тестовом окружении нужны E2E_LIVE_API=1 и E2E_STORAGE_STATE с сохранённой сессией тестового администратора; файл содержит cookie и не должен попадать в Git.
