# Запуск, миграции и проверки

Команды ниже относятся к локальной разработке. Состояние файлов миграций не подтверждает их применение к рабочей БД. Последний результат проверок хранится в [CONTEXT.md](../CONTEXT.md).

## Локальный запуск

Создайте корневой `.env` по `.env.example`, затем из корня:

```sh
make sync-all
make up-dev-env
make migrate
make fastapi-dev
```

`make seed` запускается отдельно и необязательно. Создаёт демонстрационные категории, шаблоны и связанные скрытые задачи, не создаёт пользователей и не повышает права. Повтор не дублирует записи. Перед показом демозадачи нужно загрузить фото и снять `is_hidden`.

| Команда из корня | Действие |
| --- | --- |
| make up-dev-env | PostgreSQL, MinIO, minio-init, Adminer и Redis |
| make stop-dev-env | Остановить инфраструктуру с сохранением контейнеров |
| make down-dev-env | Удалить контейнеры dev-сервисов, сохранив тома |
| make up-all | Собрать backend и запустить весь Compose |
| make down-all | Остановить и удалить контейнеры, сохранив тома |
| make migrate | Alembic upgrade head настроенной БД |
| make logs | Логи backend |
| make precommit-check | Ruff, форматирование, ty и pytest |

Docker entrypoint сейчас применяет Alembic перед FastAPI с четырьмя workers. Это удобство локального запуска; при развёртывании нескольких реплик миграции нужно выполнять отдельным шагом.

## Настройки

Backend читает корневой `.env`, затем `backend/.env`; переменные процесса имеют приоритет. PROJECT_NAME и DATABASE_URL обязательны. Для обычного `postgresql://` приложение выбирает asyncpg, Alembic использует psycopg. Рабочие секреты не выводить в лог.

| Настройка | Назначение / значение по умолчанию |
| --- | --- |
| S3_ENDPOINT_URL | Адрес для backend; в Compose http://minio:9000 |
| S3_ACCESS_KEY, S3_SECRET_KEY | Учётные данные хранилища |
| S3_BUCKET, S3_REGION | codehunt, us-east-1 |
| MAX_PHOTO_BYTES | 5 МиБ; значение выше 5 МиБ ограничивается этим максимумом |
| MAX_RESOURCE_BYTES | 50 МиБ |
| REDIS_URL | Без значения кеш отключён; Compose задаёт redis://redis:6379/0 |
| MEDIA_CACHE_TTL | 300 секунд, допустимо 1–86400 |
| MEDIA_CACHE_MAX_BYTES | 1 МиБ; диапазон 0–5 МиБ, более крупные файлы не кешируются |
| GITHUB_ID, GITHUB_SECRET | То же OAuth-приложение, что у frontend |
| ADMIN_EMAILS | Подтверждённые адреса администраторов через запятую |

Порты по умолчанию: Redis 6379 (loopback), PostgreSQL 5433, backend 8000, MinIO API 9000, MinIO Console 9001, Adminer 8080. PostgreSQL использует том app-db-data, MinIO — app-minio-data. minio-init повторяемо создаёт приватный бакет. Redis ограничен 256 МиБ, использует allkeys-lru и не сохраняет кеш на диск; его сбой не блокирует чтение из MinIO.

## GitHub OAuth

1. В GitHub OAuth App задайте callback `http://localhost:3000/api/auth/callback/github`; для production — HTTPS-адрес frontend. Hostname браузера, NEXTAUTH_URL и callback должен совпадать.
2. В frontend `.env.local` задайте GITHUB_ID, GITHUB_SECRET, NEXTAUTH_URL и случайный NEXTAUTH_SECRET. BACKEND_API_URL задаёт внутренний адрес backend; запасной вариант — NEXT_PUBLIC_API_URL, затем localhost:8000. Секреты не должны иметь префикс NEXT_PUBLIC.
3. Backend получает те же GITHUB_ID/GITHUB_SECRET и ADMIN_EMAILS. Пустой список означает отсутствие администраторов. Регистр и окружающие пробелы в адресах игнорируются.
4. Примените миграции в рамках развёртывания и перезапустите приложения. Первый вход создаст аккаунт по github_id. Существующая запись не связывается с GitHub автоматически по совпадению email.
5. После изменения email в GitHub выйдите и войдите снова: список подтверждённых адресов обновляется при входе. Роль по ADMIN_EMAILS проверяется backend при запросах, поэтому отзыв административного доступа не ждёт следующего OAuth-входа.

Backend проверяет принадлежность GitHub-токена своему OAuth-приложению. GitHub-токен не хранится; backend выдаёт сессию на 24 часа и сохраняет только хеш. NextAuth v4 отвечает за OAuth state/PKCE/CSRF и зашифрованную HttpOnly cookie. Backend-токен не возвращается в `/api/auth/session`. Прокси игнорирует пользовательские Authorization/X-User-ID и проверяет Origin записывающих запросов.

## Файлы и лимиты

Фото доступны по GET/HEAD `/api/media/photos/{id}`, вложения — `/api/media/resources/{id}`. Проверка владельца, видимости и платного доступа предшествует Redis и 304. Ответы `private, no-cache` допускают браузерное хранение, но требуют повторной проверки. Не добавляйте общий CDN/Next Image Optimization для закрытых файлов без эквивалентной авторизации.

Небольшие файлы читаются ограниченным буфером и кешируются; более крупные передаются из S3 блоками 64 КиБ с закрытием соединения при отмене. JSON-ответы используют no-store. Next.js ограничивает запросы по маршрутам: JSON — 2 МиБ, пакет фото — 21 МиБ, ресурс — 51 МиБ. Backend имеет единый технический предел 64 МиБ без разбора маршрутов. Оба слоя проверяют Content-Length и фактическое число байтов. Максимум одного фото — 5 МиБ, одного ресурса — 50 МиБ; дополнительный 1 МиБ предназначен для multipart-обрамления. При превышении возвращается 413. Таймаут 120 секунд применяется в Next.js-прокси, SSR имеет таймаут 15 секунд. Middleware backend ограничивает только размер; для прямого доступа таймаут получения тела должен задаваться входным сервером. Правила Cache-Control вынесены в отдельный ResponseCacheMiddleware.

Удаление сохраняет ключи в pending_file_deletions в транзакции метаданных. После commit выполняется попытка удаления, при сбое — повтор каждые 60 секунд, до 100 ключей за проход. Ссылки обеих таблиц файлов проверяются одним пакетным запросом. attempt_count отражает зафиксированные попытки, не внутренние повторы boto3; после успеха запись удаляется. Старые объекты без метаданных автоматически не ищутся.

## Тесты и статические проверки

Нужен работающий Docker. Testcontainers запускает отдельные PostgreSQL 18, MinIO и Redis на свободных портах. Рабочие тома, БД и seed не используются. Из backend:

```sh
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run pytest --cov=app --cov-report=term-missing
```

Можно использовать уже синхронизированные `.venv/bin/...`. Порог coverage — 80%. Фикстура создаёт схему через Base.metadata.create_all и удаляет через drop_all. Проверки миграций выполняют преобразования только в тестовой БД; историческое исключение с ручной схемой в test_template_slug.py описано в плане.

Из frontend:

```sh
npm run lint
npm run typecheck
npm test
E2E_ISOLATED_AUTH=1 PLAYWRIGHT_CHANNEL=chrome npm run test:e2e -- --grep-invert @live
npm run build
```

Изолированный Playwright запускает Next.js на 3100 и тестовый backend на 8101; реальные GitHub, БД и MinIO не нужны. Фикстуры SSR передаются тестовому backend, поскольку browser.route не перехватывает серверный fetch. Для Webpack-сборки явно передайте `-- --webpack`.

## Live E2E с одноразовым backend

Из frontend:

```sh
PLAYWRIGHT_CHANNEL=chrome npm run test:e2e:live
```

Или из backend: `PLAYWRIGHT_CHANNEL=chrome uv run python scripts/test_live_e2e.py`.

Скрипт создаёт отдельные PostgreSQL/MinIO/Redis, настоящий FastAPI и временную копию frontend без рабочих `.env`, использует свободные порты. Схема создаётся через create_all/drop_all. Тестовый администратор получает настоящую запись backend-сессии и зашифрованную cookie NextAuth без обращения к GitHub. Три сценария @live проверяют черновик, фото/вложения, публикацию, редактирование, удаление и конфликт revision. Контейнеры и копия удаляются после прогона; путь к логам и Playwright-артефактам выводится командой.
