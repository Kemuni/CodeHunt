# Оставшиеся задачи

Состояние на 10.11.2026. Текущая реализация описана в [модели](task-domain-model.md) и [API](api-contracts.md), результаты последней проверки — только в [CONTEXT.md](../CONTEXT.md). Перечень ниже не означает разрешения автоматически расширять объём работы.

## Перед публичным развёртыванием

1. Подготовить применение миграций к конкретной БД: выяснить её revision, сделать резервную копию, проверить пользователей без github_id. Новая `72ad0e81f630` удаляет Task.status с переносом архивных задач в скрытые. Проверить старые деревья глубже трёх групп: они читаются, но новый редактор/API не позволят сохранить их без сокращения вложенности. Детали — в [development.md](development.md).
2. Разделить dev/prod конфигурацию. Текущий Compose публикует PostgreSQL, MinIO и Adminer; MinIO имеет локальные значения учётных данных по умолчанию. Нужны закрытая сеть инфраструктуры, отдельное управление секретами, фиксированные образы, TLS-вход и согласованные с приложением лимиты запроса. Убрать dev-зависимости из runtime-образа, предварительно перенеся psycopg, необходимый Alembic, в runtime. Запуск миграций вынести из старта каждой реплики в отдельный шаг развёртывания.
3. Проверить реальный OAuth в целевом окружении: callback, hostname, HTTPS cookie, подтверждённые email и отзыв административного доступа. Автотесты не используют реальные GitHub-аккаунты.

Готовность: новое приложение запускается на копии существующих данных, старые архивные задачи остаются закрытыми, авторизация проверена на целевом домене, служебные сервисы не доступны из публичной сети.

## Устойчивость редактора и файлов

| Ограничение | Возможная следующая работа | Критерий готовности |
| --- | --- | --- |
| У Task нет revision, устаревший PUT может перезаписать чужое изменение | Добавить версионирование существующей задачи | Два редактора не теряют изменения молча |
| После успешного publish и потери ответа повтор возвращает 404 | Ввести ключ идемпотентности с привязкой к владельцу и результату | Повтор возвращает ту же созданную задачу |
| Аварийное прерывание загрузки/неуспешная компенсация может оставить объект без метаданных | Учёт незавершённых загрузок или отложенная сверка MinIO | Старые сироты удаляются без риска для используемых ключей |
| Часть операций формирует ответ после commit | Проверить границы записи и чтения ответа при сбоях | Ошибка ответа не провоцирует неуправляемый повтор мутации |
| Ссылки на шаблоны в JSON черновика не имеют версии | При необходимости сохранять версию/снимок текста | Изменение источника явно обнаруживается до публикации |

Очередь удаления файлов после commit уже реализована: повторяет сбои, считает попытки и пакетно проверяет ссылки. Она не заменяет поиск объектов, у которых никогда не было зафиксированных метаданных.

## Проверки и сопровождение

- `test_template_slug.py` создаёт часть старой схемы вручную и выполняет миграцию в отдельном PostgreSQL-контейнере. Это прежнее исключение из обычного подхода create_all/drop_all. При переработке миграционных тестов отделить их назначение от CRUD-тестов; не подменять проверку реального преобразования простым тестом новой схемы.
- Каталог остаётся клиентским: SSR реализован для детальной страницы задачи. Если понадобится индексируемый каталог с фильтрами, отдельно спроектировать URL-параметры и начальную серверную выборку.
- Для изображений добавлена отложенная загрузка. Генерация вариантов размера, CDN и signed cookies остаются отдельной задачей; текущую проверку доступа нельзя обходить общим кешем изображений.
- Биллинг не реализован. Платные задачи закрыты для всех, кроме администраторов. Будущий доступ по подписке должен одинаково применяться к спискам, деталям, пресетам, файлам и решениям.

## Сохранённые решения

Отдельные GET пресетов и `parent_task_id` оставлены по прямому указанию пользователя. API решений и независимые снимки сохраняются для будущего интерфейса. Автоматического наследования задач от родителя нет.

Не возвращать Task.status, Task.draft, schema_version, slug шаблонов, сохранённую нумерацию пунктов задания или второй загрузчик файлов без новой задачи. Не делать поля Task необязательными ради сохранения незаконченной формы: для этого есть TaskDraft.

Обновлять документацию по назначению: модель — правила данных, API — контракты, development — команды и миграции, CONTEXT — короткая передача и единственный текущий результат проверок, этот план — только оставшиеся работы.
