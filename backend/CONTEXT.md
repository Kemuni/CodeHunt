## Принятые решения

Нумерация состава: только position хранится в БД у пунктов и групп. order_number пунктов вычисляется в API при чтении сверху вниз с 1 внутри каждого уровня, у групп его нет. Порядок исторических снимков в решениях хранится отдельно и не пересчитывается из задания.

1. `User` связан с GitHub ID, сессии на 24 часа хранятся в auth_sessions. Администраторы — подтверждённые email из ADMIN_EMAILS; X-User-ID удалён. CRUD пользователей вне объёма. Админ видит все Task, но только свои TaskDraft. Пользователь видит только свои решения.
2. `TaskComplication` — общий смысл требования для администратора: category_id, title, description. Нет slug и help_text. Категория имеет parent_id и developer_type, но не type и не group.
3. `TaskComplicationLink` — конкретное применение шаблона: title, description, acceptance_criteria, level, is_required. complication_id необязателен, один шаблон допускает несколько применений в одном Task. Стек и логическая совместимость пунктов не проверяются.
4. Используемый шаблон нельзя переименовать или изменить его description. При смене текста связанного конкретного пункта клиент явно подтверждает complication_id, выбирает другой или передаёт null. Семантического анализа текста нет. Ссылка из JSON черновика сама по себе не блокирует изменение/удаление шаблона.
5. Группы вложенные, с обязательным level. Все потомки одной группы имеют тот же уровень. Это обеспечивают Pydantic и составные FK с task_id, level. Лимиты: 10 уровней и 1000 элементов.
6. Пресеты easy/medium/high накопительные при создании решения. В деталях задачи каждый уровень показывает только собственные пункты. TaskLevelPresetComplication не нужна. Сами группы привязаны к Task и level, а не к строке пресета.
7. difficulty_from/to и difficulty_rating — целые 0–10 включительно. Авторство дизайна необязательно. parent_task_id показывает происхождение, например fullstack от frontend, без наследования данных.
8. TaskDraft — вся незавершённая форма в JSONB плюс фото и вложения отдельными строками. Владелец назначается сервером. revision обязателен для каждой мутации, ошибки пересчитываются при чтении и сохранении. schema_version нет.
9. Файлы принадлежат ровно Task или TaskDraft через task_id/draft_id. Публикация создаёт Task, дерево и пресеты, переносит привязки файлов и удаляет форму одной транзакцией. ID и ключи объектов сохраняются. /materialize удалён, используется /publish.
10. Task имеет published/archived и независимый is_hidden. Публичный API скрытое/архивное задание не показывает даже по прямой ссылке. Уже созданные решения остаются доступны авторам.
11. Фото максимум четыре, первое титульное. Списки Task: cover_photo. Детали: cover_photo + photos + resources. URL фото и вложений постоянные через /api/media/photos/{id} и /api/media/resources/{id}, expires_in удалён. Оба типа файлов кешируются с проверкой доступа. object_key наружу не выдаётся.
12. Решение можно создавать многократно для одного задания. description изначально пустая строка, GitHub и рейтинг nullable. Любые пункты можно исключить, в том числе is_required. Собственный пункт не ссылается на шаблон.
13. Тексты задания, пресета и требований копируются в решение и не синхронизируются с источником. Завершение решения и пунктов независимо через resolved_at. Статус решения генерирует PostgreSQL. Файлы в историческом снимке решения не фиксируются.

## Последние изменения кода

- `TaskDetail.presets` теперь объект easy/medium/high с блоками `{preset, complications}`. preset может быть null, пустые группы остаются в своём уровне. Старый массив presets и верхнеуровневый complications в ответе деталей больше не используются.
- `TaskComplicationLinkGroup.level` обязателен, смешанные по уровням группы запрещены. Полный PUT composition сохраняет существующие ID.
- У `TaskComplication` удалён slug во всех схемах, ORM, поиске и seed. `Task.slug` остался.
- `media.discard_upload` пытается откатить БД и удалить каждый новый объект даже при ошибках самой очистки, не подменяя исходную ошибку. Ошибка размера загрузки теперь явно проверяется тестами.
- `Storage.stat` возвращает типизированный ObjectMetadata с ContentLength. Boto3-типы импортируются только для проверки типов.
- В библиотеке категории сгруппированы по developer_type. Родитель другого направления не включается в группу ребёнка, parent_id сохраняется.

## Кеширование вложений — 08.11.2026

Фото и вложения используют общий MediaCache (services/media_cache.py), общий доступ и чтение байтов в services/media.py. Вложения задач и черновиков доступны по /api/media/resources/{id} и административному /api/editor/media/resources/{id}; URL сохраняется при публикации.
